## Role of the bundle

SeedKit processes personal data only on behalf of the host application (as part of its processing): the documents of
providers whose schema marks fields with `x-seed-personal-data: true` (for example CRM contacts). The data itself
belongs to the host and is read and written by the host's providers through the host's handlers. SeedKit adds no
purpose, sends nothing anywhere and makes no outbound call.

## Personal data in documents

- Mark every field that holds personal data with `x-seed-personal-data: true`. The export template lists those fields
  in its header comment ("Personal data: name, email, phone").
- Natural keys may be personal data (an e-mail address); they are treated as such below.
- Providers filter by the actor: export, plan and prune only the rows the actor may read and write.

## What SeedKit stores

| Data | Where | Retention |
| --- | --- | --- |
| Uploaded / read documents | Not stored in 0.1: the console reads the file into a temporary stream that is gone after the command | — |
| Run history | `<prefix>seed_run`: actor ref, scope, providers, counts, document hash, plan hash, batch digests, status, error code, timestamps. No item, no natural key, no value | `runs.history_days` (365) via `runs:purge` |
| Leases | `<prefix>seed_lease`: provider, scope, run id, expiry | Overwritten by the next run |

The `document` column of the run table stays empty in 0.1; the 0.2 upload flow keeps a normalised document for at most
one hour while a run is planned and deletes it when the run ends (contract Q-SK-5).

## Exports

- An export of the **current rows** of a provider with personal-data (or secret) fields is audited: who, provider,
  scope, row count. Templates and other exports are only logged at `info`.
- File names generated by the console are yours (`--output`); the 0.2 UI builds download names from the provider, the
  scope kind and a timestamp only, never from personal data, and shows a notice before such a download.
- Handle exported files according to your policy: they contain personal data; prefer `var/seeds` (not versioned) over
  `config/seeds` for current exports.

## Errors, logs and audit

- Row errors name the row index, the natural key, the field pointer and the rule, never the value. The natural key is
  shown to the operator who runs the command (and to the uploader in 0.2), and **never logged**.
- Log records, events and audit entries carry no item, natural key, value or file name. A provider or database failure
  during an apply is logged with the exception class and code only: driver messages quote row values.
- Audit retention is the sink's (your log retention, or AuditKit's).

## Erasure

- `nowo:seed-kit:actor:forget <ref>` nulls the actor reference in every run of that actor; the history (counts,
  hashes) stays.
- After `runs:purge` nothing of a run remains.
- SeedKit holds no data subject records of the host: erasing a contact's data stays with the host (and its CRM).
  Re-applying an old seed file could bring erased data back: remove erased subjects from the seed files you keep.

## Consent and lawful-basis fields

A seed must not create or change consent records unless the host decides so. Mark consent and lawful-basis fields
`x-seed-readonly: true`: they are exported for context and ignored on import (QB-SK-4).

## Host checklist

- Personal-data fields marked in every provider schema; consents read-only.
- Who may export (`SEED_EXPORT`) mapped narrowly for providers with personal data.
- Audit sink retention and access defined.
- `runs:purge` scheduled (cron) and `actor:forget` part of your erasure procedure.
- Exported files kept out of version control and deleted when no longer needed.
